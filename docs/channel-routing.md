# 多渠道与模型设置

1.4.2 为 Antigravity 2.33.0 的桌面主 Agent 增加渠道聚合。首次安装默认进入本地工作区，无需登录或配置提供商。选择 API 聚合渠道后，按渠道配置服务地址、协议、密钥和模型；选择官方服务时继续按官方流程登录。已有配置缺少新版接入方式字段时，沿用原有官方或聚合模式。模型与模式变更须完全退出并重新启动 Antigravity，使原生模型配置重新加载。

四种协议分别适配 OpenAI Chat Completions、OpenAI Responses、Anthropic Messages 和 Gemini。它们接入桌面主 Agent 的原生工具流程，工具执行继续受原生审批和权限设置控制。渠道服务的模型能力、配额和账单由相应服务决定。

每个模型的最大输入默认 275,000 tokens，最大输出默认 125,000 tokens，均可修改。输入上限通过原生上下文控制生效；输出上限映射到各协议实际请求字段。设置值不能提高服务端本身的上限，需按使用的模型能力调整。

| 协议 | 输出上限字段 |
|---|---|
| OpenAI Chat Completions | `max_completion_tokens` |
| OpenAI Responses | `max_output_tokens` |
| Anthropic Messages | `max_tokens` |
| Gemini | `generationConfig.maxOutputTokens` |

强度滑条显示当前模型实际配置的全部档位，不把所有模型强制映射成相同档位数；标签保留英文。Ultra 档位的粒子向右发射。动画默认遵循系统的减少动画偏好，用户主动点击闪电开关可覆盖系统默认，单独启用或关闭动画。

闪电开关通过原生 `storageService` 保存选择，避免应用本机服务端口变化导致浏览器 `localStorage` 的偏好失效。

渠道配置和密钥保存在接收者本机，不进入源码仓库、截图或安装包。配置服务时使用自己的有效密钥。四协议先完成本机流程验证；后续真实 OpenAI Responses 渠道的连接修复已由用户确认，其余真实协议与模型尚未逐一验收。

已在实际运行的 Antigravity 中操作以下流程；渠道端使用本机服务替身：

- 四协议分别完成 `read_file → 原生审批 → 工具结果 → 正确最终回答`。OpenAI Responses 的 encrypted reasoning 和 Anthropic 的 thinking signature 均在原生跨工具轮次中保留。
- 实际拖动滑条选择 Ultra，模型显示 Ultra，渠道收到 `reasoning_effort: ultra`。动画启用时 14 个粒子运行，系统减少动画默认生效时粒子停用。
- 中文与英文双向切换；渠道新建、编辑、删除、获取模型，以及编辑时空密钥保留已保存密钥。
- 275,000／125,000 默认上限和 300,000／64,000 修改值保存。原生模型 catalog 的输入上限为 300,000；Anthropic 实际请求的 `max_tokens` 为 64,000。
- 禁用聚合并重启后恢复原生官方模型，启用并重启后恢复聚合模型。
- 1.4.0 更新安装和完整卸载成功退出。卸载后原厂归档 SHA256 完全恢复，既存渠道密钥、Goal 和会话状态保留。

最终 1.4.0 安装包也完成重新安装，成功退出。动画开关通过完整退出与重启后的原生存储恢复，应用本机端口变化后仍保持开启，14 个粒子继续运行。协议转换另检查了推理签名按渠道、模型与协议隔离、纯文本回合保留、重复同名工具调用的结果 ID 配对，以及 SSE 的 CRLF 跨数据块处理。

最终安装包的完整卸载成功退出：原厂归档与安装前原件 SHA256 完全一致，既存配置、会话状态和四份加密渠道密钥逐项保持原 SHA256，官方可执行文件保留。

这些结果验证原生应用与本机协议转换的闭环；真实服务端对模型、推理档位、媒体和额度的支持仍需使用有效渠道密钥确认。

架构参考为 MIT 项目 [CC Switch](https://github.com/farion1231/cc-switch/tree/6e06607290b805ff2d0b92fa4e6bc69526f5e740)，本项目未直接内置其应用。中文化中仍有少量第三方与服务端动态英文文案；原生工作流环境未开放 `call_tool` 时，实验性 JS 桥仍不能用于真实工具调度。

1.4.1 已完成本机更新安装、无提供商本地工作区启动与重启，以及设置入口操作。独立空白配置无需登录即可进入工作区，添加本机模拟 Gemini 渠道并重启后，完成 read_file、逐次审批与工具结果回传。官方模式使用原生认证及引导页面。Windows EXDEV 替换失败复用原生存储的已有写入回退，其他错误继续上抛；渠道配置也仅为该错误提供回退。安装启动器已验证可写临时目录、PowerShell 模块路径隔离及参数传递。

1.4.2 将接入方式改成始终可选的三个选项。没有提供商时选择 API 聚合会直接展开新渠道表单，保存并启用会在同一次配置写入中保存渠道并启用聚合；取消不会改变已保存的模式。已通过实际空白配置操作验证选择、填写、保存、自动启用及 275000/125000 默认参数。界面按接入方式、渠道编辑和控制器分模块，保持原生主题；模型参数采用双列布局，思考强度 API 参数按需展开。

## 1.4.3 渠道与会话修复

真实 Responses 请求携带原生工具时曾返回 HTTP 400。原生 JSON Schema 包含可选参数，现在显式传递 `strict:false`，避免默认严格校验改变原生参数语义。用户已确认连接正常，实际界面出现 GPT 模型回复及工具执行。固定 16 工具的独立诊断请求仍曾返回上游通用 400；它与真实会话的动态工具、系统提示和历史不同，因此不能认定 schema 是唯一根因，也不能宣称全部请求均已修复。Chat adapter 同时补传 route，使思考历史按原有渠道、模型和协议规则匹配。

上游失败保留 HTTP 状态和经脱敏、限长处理的错误详情，避免全部显示成通用服务不可用。认证失败、限流和模型不存在可据此分别诊断。用户配置的另一个 Gemini 模型曾被上游返回“无可用渠道”，这属于该模型的渠道可用性，不能从 GPT 连接成功推断其也能使用。

普通渠道模型菜单按模型合并显示，思考档位仍保留完整内部路由。已有截图确认 8 个模型显示为 8 项，不再展开成 44 项；当前真实界面显示 gpt-6.1-sol High。High / Ultra 的选中与重开菜单路径已静态审阅，中英文构建保留英文档位标签。本轮用户正在使用，未重复现场拖动 Ultra 或重启软件。

真实会话在多次工具执行后出现 JSON 解析错误：一个 5,053 字节的自有思考状态被原生流合并为 63 份、共 318,339 字节。现在 Responses 和 Anthropic 每次只发送新增思考项，历史解码按完整 JSON 边界读取并去重，逐个核对渠道、模型与协议；损坏尾部仍报错。已使用该真实会话签名验证恢复一份原始思考项，完整内容一致，原生历史到 Responses 请求转换成功。本机更新安装完成，安装记录与全部渠道文件哈希一致。

安装补丁并重启后，在发生错误的同一个旧会话里，真实 gpt-6.1-sol High 完成读取本地验证文件并回复 `OMA_REASONING_OK`，渠道状态无失败。期间出现一次上游网络连接失败，原生重试后完成；该结果验证旧会话恢复及真实工具闭环，不代表所有上游请求或模型均可用。

## 1.4.4 缓存复用

参考 [Codex client.rs](https://github.com/openai/codex/blob/076ac7856b1235947f271930bd7437bae54a0dfc/codex-rs/core/src/client.rs) 的稳定会话缓存标识与历史内容身份，OpenAI Responses 和 Chat 请求现在携带 `prompt_cache_key`。标识由原生请求的明确会话身份派生，按渠道、服务地址、协议和模型隔离，不含密钥；未发现会话身份时不伪造随机标识。它帮助上游维持缓存路由，不能代替相同的提示前缀。

工具定义按名称排序，JSON 对象键稳定序列化，消息、数组和工具调用顺序保持原样。缺失 ID 的历史调用改为按调用序号、名称和参数派生稳定 ID，同名同参多次调用仍有不同 ID；已有 ID 原样保留。签名、工具结果和必要上下文不删减。继续使用 `store:false`，缓存不要求在提供商持久保存整个会话，也不依赖 `previous_response_id`。

渠道服务保留最多八条内存诊断和六十四个会话的内容摘要：系统与工具是否变化、相同历史项数量、服务端实际输入和缓存用量。诊断不存提示词、正文、思考签名、密钥或明文会话 ID；没有服务端缓存计数时记为未知，不制造命中。记录通过现有设置服务的 `status.cacheRequests` 读取，不增加模型工具。

真实 gpt-6.1-sol High 验证中，首轮成功请求的缓存为 0；工具结果回传后的请求输入为 16,983 tokens，服务端报告 cached_tokens 为 16,768，命中率 98.73%。系统提示与工具定义相同，前 30 个历史项保持一致，文件读取和最终回答完成。这是该渠道该次请求的实际结果，后续命中仍取决于上游路由、缓存存活时间、提示变更和模型服务支持。

继续在同一会话验证，后续两次成功请求分别命中 98.21%（16,768 / 17,073）与 98.30%（16,896 / 17,188）。一次上游请求失败经原生重试后完成；重试沿用相同缓存身份及全部历史前缀。

本轮发现原厂自动更新在退出时安装 2.34.0，覆盖社区接入。已使用固定校验的原厂安装器恢复 2.33.0并重新安装增强内容；现在只禁止退出时自动安装更新，保留原生更新检查及主动更新入口。社区增强仍只适配 2.33.0，主动更新前需确认新版适配。
